## /wisdom-space 刷新卡 boot-screen 0%：真正的根因（boot-screen 移除逻辑缺陷）

**用户报告**：首页能进（截图证实 LandingPage 完整渲染），从首页跳智慧空间也能进，但刷新 `/wisdom-space` 卡 boot-screen 0% 永远不动。

**关键证据**：dist/index.html 自带 boot-screen div：
```html
<div id="boot-screen">  <!-- z-index: 2147483647, position: fixed, 浅米色 #f8f5f0 -->
  <div class="boot-ring">木</div>
  <div class="boot-title">木雅藏语AI助手</div>
  <div class="boot-status">正在加载应用…</div>
  <div class="boot-bar"><div class="boot-bar-inner"></div></div>
  <div class="boot-percent">0%</div>  <!-- 静态 0%，无 JS 更新 -->
</div>
```

**根因**：
1. boot-screen 用 `position: fixed; z-index: 2147483647`，永远在最顶层
2. boot-percent 是静态 0%，内嵌 JS 只在 10 秒后改 boot-status 文案，**没有更新进度数字**
3. 编译后代码（`dist/assets/index-CxF-rbOQ.js`）里 boot-screen 移除逻辑只在 LandingPage 的 `wBt` hook 内（`useFadeOutOverlay`）
4. **`/wisdom-space` 路径下 LandingPage 从未挂载** → `wBt` 从未运行 → boot-screen 永远不被移除 → 永远挡住 HomePage 渲染的内容
5. 从首页跳智慧空间：LandingPage 卸载时 cleanup `() => a.remove()` 会触发，boot-screen 被移除 → 能看到 HomePage 的深蓝 LoadingScreen

**已修**（`src/main.tsx`）：在 React 启动时无条件移除 boot-screen（淡出 0.4s 后 remove），不依赖任何特定路由组件：
```tsx
const bootScreen = document.getElementById('boot-screen');
if (bootScreen) {
  bootScreen.style.transition = 'opacity 0.4s ease';
  bootScreen.style.opacity = '0';
  window.setTimeout(() => bootScreen.remove(), 450);
}
```

**部署**：本地 `npm run build` 后把新 `dist/` 覆盖到 autodl 即可。server/index.ts 不需要重传（之前传过了）。

**教训**：
- SPA 启动屏（boot-screen）必须由 main.tsx 无条件移除，**不能依赖某个特定路由组件**，否则任何"非默认路由"刷新都会卡 boot-screen
- boot-percent 是静态数字，内嵌 JS 必须能更新它才有意义；否则弱网下用户看到的永远是"0%"

## 关键发现：body 末尾 inline script 还是会闪一帧（20:37）

**症状**：用户反馈"还是会先闪一下"——即使在非首页路径上把 boot-screen 立即 `removeChild` 并设深蓝背景，还是看到米白色一闪。

**根因**：HTML 解析器解析到 `<body>` 里的 `<div id="boot-screen">` 时**会立即渲染一帧**（因为该 div 在 CSS 里是 `position:fixed; inset:0; z-index:2147483647`），即使后面 body 末尾的 inline `<script>` 同步执行 `removeChild` 把它从 DOM 移除，浏览器也已经绘制了那一帧。

**正解**（已实施，`dist/index.html` 第 12-25 行）：

在 `<head>` 里**最优先位置**（`<style>` 标签之前）同步阻塞执行 inline `<script>`：

```js
(function () {
  var p = location.pathname;
  var isLanding = p === '/' || p === '/index.html' || p === '';
  if (isLanding) return;
  var s = document.createElement('style');
  s.textContent = 'html,body{background-color:#0a0e27!important}#boot-screen{display:none!important}';
  document.head.appendChild(s);
})();
```

**原理**：
1. HTML 解析器遇到 `<script>` 同步阻塞执行（无 `defer`/`async`）
2. JS 立即创建 `<style>` 标签插入 head → CSS 同步生效
3. 解析器继续解析下面原 `<style>`（含 `#boot-screen { background:#f8f5f0 }`），但被追加的 `!important` CSS 覆盖
4. 解析到 `<body>` 里的 boot-screen div → CSS `display:none` 已就位 → **不渲染任何帧**

**关键教训**（写进 MEMORY 也值得）：要"不绘制某元素"，必须在它出现在 DOM 之前就准备好对应 CSS，**不能依赖 DOM 操作移除**——因为 HTML 解析器边解析边绘制，每出现一个元素就是一帧。

## DeepSeek-V3 401 invalid_api_key 调试（20:46 起）

**用户报告**：`/api/chat` 之类的接口返回 Aliyun 401，错误信息是 `Incorrect API key provided`。key 写成 `sk-08d5d4125fee4c14bb4b03b526ab98e4`，curl 直接打 dashscope 端点**能成功**返回 `"Hello! 👋"`。

**关键证据**（决定性的一刀）：
```bash
$ cat /proc/47743/environ | tr '\0' '\n' | grep -i ALIYUN
[空]
```
**Node 进程环境变量里根本没有 `ALIYUN_API_KEY`**。不是 key 不对，是 Node 压根没拿到。

**根因**：
- `/root/.muya-env` 里 key 是好的（`cat -A` 验证无尾巴字符）
- 但 cron `@reboot sleep 30 && tsx server/index.ts` 和保活 `*/5 * * * *` 的启动命令里**没有 `source /root/.muya-env`**
- `/root/.muya-env` 用的是 `export KEY=VALUE` 格式（不是 dotenv 的 `KEY=VALUE` 裸格式），**只对当前 shell 生效，不会被子进程继承**，必须显式 source
- 结果：Node 启动时 `process.env.ALIYUN_API_KEY === undefined` → `ALIYUN_CONFIG.apiKey` 是 undefined → fetch 时 `Authorization: Bearer undefined` → Aliyun 401

**修复路径**：
1. 临时：`source /root/.muya-env && tsx server/index.ts` 重启 Node
2. 持久：改 cron 启动命令加 `source /root/.muya-env &&` 前缀
3. 根治：在 `server/index.ts` 顶部加 `import 'dotenv/config'`（或手写 parse `/root/.muya-env` 的 `export X=Y` 行），让 Node **自己加载 env，不依赖启动脚本**——这才是"挂上去就不用管"的方案

**debug 套路总结**（值得复用）：
- API key 类 401 → 先 `cat -A <env文件>` 确认 key 干净 → 再 `curl -s <endpoint>` 用 key 直打确认 key 有效 → 然后 `cat /proc/<PID>/environ | tr '\0' '\n' | grep -i <KEYNAME>` 看 Node 进程实际有没有这个变量
- 99% 的 401 不是 key 错，是 env 没传到进程

**教训**：跨进程 env 配置文件如果用 `export X=Y` 格式（bash 友好），必须 `source`；启动脚本里忘记 `source` 是 401 第一大原因。建议 server 代码直接 `import 'dotenv/config'` 一劳永逸，**别把 env 加载的责任推给运维脚本**。

**待办**：等用户 `crontab -l` 输出后帮改 cron；之后视情况帮 server 加 dotenv 兜底。

## B 方案落地：env-loader.ts（20:50 用户采纳）

**用户的"挂上去就不用管"诉求**：env 不应该依赖 cron 启动命令 `source /root/.muya-env`，server 应该自己读。

**实现**（2 个文件改动，零新依赖）：

1. `server/env-loader.ts`（**新增 74 行**）：
   - 用 `node:fs`（内置模块）读 `/root/.muya-env` → `/root/.env` → `.env` 三个候选路径，命中第一个就停
   - 正则 `^(?:export\s+)?([A-Z_][A-Z0-9_]*)\s*=\s*(.*?)\s*$` 同时支持 bash `export KEY=VALUE` 和 dotenv `KEY=VALUE` 两种格式
   - 处理 `#` 注释、空行、首尾引号包裹的 value
   - **`if (key in process.env) continue`**：运行时通过 `/api/_debug` 那条 `process.env.ALIYUN_API_KEY = apiKey` 设的 key 优先，loader 不覆盖
   - 找不到 env 文件 → 只 log 不报错（开发场景 OK）

2. `server/index.ts` 第 1 行：加 `import "./env-loader.js"`（必须 `.js` 后缀，tsx ESM 解析规则）

**为什么不直接用 dotenv 包**：
- autodl 拉回来的 `node_modules` 可能残缺（之前 build 时 tsc 找不到 lib 就是这个原因）
- 多一个依赖多一个风险
- 自己写 30 行逻辑可控性更高

**效果**：
- ✅ cron / docker / 手敲命令启动 Node 都能自动拿到 env
- ✅ 不依赖 `source /root/.muya-env` 前缀
- ✅ 容器重启后无需额外操作

**部署动作**：scp 两个文件到 autodl → kill 旧 PID → npx tsx server/index.ts 启动 → `cat /proc/<新PID>/environ | grep ALIYUN` 验证

## 最终收尾：端口漂移根因 + 一条龙 sed 修复（21:12 全部验证通过）

**部署过程中的两个新坑**：

1. **scp 命令贴错终端**：用户把本该本地 Windows 跑的 scp 贴到 autodl bash 里，`root@<autodl>` 的 `<` 被当成重定向 → `bash: autodl: No such file or directory`，index.ts 没传上去。
   - **教训**：给用户的命令块要明确标注"在哪台机器上跑"；占位符 `<xxx>` 在 bash 里是重定向语法，容易炸。

2. **bash 中文注释 + 换行丢失**：`kill 47743 # 注释（...）` 粘贴时换行丢失变成 `sleep 5# 3) ...`，`)` 变成语法错误 `bash: syntax error near unexpected token ')'`，kill 没执行。
   - **教训**：给用户的多行命令块：命令后**不要接行内注释**，注释只独占一行；整块可一次粘贴。

3. **端口漂移根因**：`server/index.ts:70` 的 `const PORT = parseInt(process.env.PORT || "3001")`，**默认 3001**。之前 6020 是靠启动命令带 `PORT=6020` 环境变量。手动重启没带 → 掉回 3001 → cpolar 隧道（指向 6020）Tunnel unavailable。
   - **修复**：`echo 'export PORT=6020' >> /root/.muya-env` 永久固化。

**最终修复命令块**（全部在 autodl 上跑，不需要 scp）：
```bash
grep -q 'env-loader' server/index.ts || sed -i '1s|^|// env auto loader\nimport "./env-loader.js";\n\n|' server/index.ts
grep -q '^export PORT=' /root/.muya-env || echo 'export PORT=6020' >> /root/.muya-env
```
两个 `grep -q ||` 守卫保证幂等（重复跑不会重复插入）。

**最终验证结果（21:12 全绿）**：
- index.ts 头部有 `import "./env-loader.js"` ✅
- `/root/.muya-env` 有 `PORT=6020` + `ALIYUN_API_KEY` ✅
- 服务器监听 **6020**（3001 消失）✅
- 进程 env 有 `ALIYUN_API_KEY` + `PORT=6020` ✅
- `[env-loader] 加载了 0 个环境变量` = 正常（source 先注入了，loader 尊重已有值跳过；cron 重启忘 source 时 loader 才兜底加载）

**架构层面的最终状态**：
- env 加载三层保险：① 启动命令 `source`（主要）② env-loader.ts 自动读（兜底）③ `/api/_debug` 运行时设置（最高优先，不被覆盖）

**遗留**：autodl 上的 index.ts 头部注释（`// env auto loader`）跟本地版本（中文两行注释）略不一致，功能等价。下次整目录同步时会自然统一。

## "你好"两次回答不一致问题定性（21:20 curl 实测，非 bug）

**现象**：用户在木小文页面问"你好"，第 1 次返回"未检索到可靠依据"（无证据），第 2 次返回 6 条不相关 CSV 证据（QA_叮嘱/QA_动词等）但无总结回答，界面右上角显示 deepseek-v3。

**curl 实测定性**（`POST /api/agent-chat`，入参 `{agentType, message}`）：
- `muxiaozhi` + "你好" → **DeepSeek 正常工作**：`model:"deepseek-v3"`、`modelBased:true`，回答"> 此回答基于模型自己的回答，请仔细辨明\n\n你好！我是木小知..."，`warning:"可信联网检索未启用"` → **401 修复确认生效** ✅
- `muxiaowen` + "你好" → `evidenceCount:0`、`model:"知识库检索"`、answer="> RAGFlow 的 muya 知识库未检索到可靠依据" → **硬拒答（设计行为）**

**结论**：
1. DeepSeek 链路已修复且正常。
2. 木小文 = 严格翻译智能体，**只认知识库证据**，"你好"不在知识库 → 拒答是设计行为（server/index.ts 1625-1638 证据闸门）。
3. 两次差异 = RAGFlow 检索波动（相似度阈值边缘），第 2 次命中 6 条不相关词条走了"证据直出"分支（1652-1669），deepseek 看 prompt（259 行规则）判断证据不足输出"知识库未检索到可靠依据"。
4. **前端右上角 "deepseek-v3" 标签不可信**（可能是固定显示），真相看接口返回的 `model` 字段：`deepseek-v3`=真调了；`知识库证据直出`/`知识库五语对照直出`/`知识库检索`/`证据闸门`=没调模型。

**诊断方法沉淀**：`curl -s -X POST http://localhost:6020/api/agent-chat -H "Content-Type: application/json" -d '{"agentType":"...","message":"..."}' | head -c 1500` 看 answer/model/warning 三个字段即可定位行为分支。
